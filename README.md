# CRM Deals Pipeline: Synthetic Data, Cleaning, SQL and Baseline ML

Junior ML Engineer test assignment (MACH TECH, AI-01). The project generates 3000 synthetic CRM deals, cleans them, loads them into PostgreSQL, answers three business questions in SQL, and trains a leakage-safe baseline classifier that predicts deal status.

> All data is synthetic and generated by `data_generation.py`. No real customer data is used.

## Project structure

| File | Purpose |
|------|---------|
| `data_generation.py` | Generates `deals.csv` (3000 deals + 9 deliberately dirty rows) and `customers.csv` (500 customers) |
| `data_cleaning.py` | Cleans `deals.csv` and writes `deals_clean.csv` |
| `to_sql.py` | Loads `deals_clean.csv` and `customers.csv` into PostgreSQL (database `crm`) |
| `Queries.sql` | Three analytical SQL queries |
| `Baseline_ML.ipynb` | Leakage-safe baseline ML, hyperparameter tuning and comparison |
| `requirements.txt` | Python dependencies |

## How to run

```bash
# 1. environment
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

# 2. generate data  -> deals.csv, customers.csv
python data_generation.py

# 3. clean          -> deals_clean.csv
python data_cleaning.py

# 4. create a .env file with your database credentials (never committed)
# DATABASE_URL=postgresql+psycopg://USER:PASSWORD@localhost:5432/crm
python to_sql.py

# 5. run the queries in Queries.sql with psql / pgAdmin / DBeaver
psql -d crm -f Queries.sql

# 6. ML notebook
jupyter notebook Baseline_ML.ipynb
```

## 1. Data generation

- **customers**: 500 rows (`customer_id`, `name`, `surname`, `city`, `age` 18-65).
- **deals**: 3000 rows (`deal_id`, `customer_id` 1-500, `amount` 500-5000, `source` in Instagram / Telegram / Facebook / Friend/Relative, `status` in Won / Lost / In Progress).

Amounts are stored as integers (no `$` sign) so they can be used directly as an ML feature.

Nine dirty rows are appended on purpose to demonstrate cleaning (3009 rows in `deals.csv`): a negative amount, missing source/status/amount, inconsistent whitespace and casing, a non-existent customer (`501`), a zero amount, an extreme amount (`999999`) and two exact duplicates (deals `3007` and `1`).

## 2. Data cleaning (`data_cleaning.py`)

| Issue | Decision |
|-------|----------|
| Whitespace / casing in `source`, `status` | `strip()` + `lower()` |
| Missing `source` / `status` | Filled with `"unknown"` (visible, not silently guessed) |
| Exact duplicate rows | Dropped (2 removed) |
| Negative amounts | Set to `NaN` (a deal cannot have a negative value) |
| Missing, zero or `> 10000` amounts | Flagged via `amount_missing` and `amount_suspicious` columns |
| `customer_id` not in `customers` | Rows dropped. A deal must belong to a customer; the reverse (customer without deals) is valid (one-to-many) |

Thresholds such as the `10000` upper limit are assumptions and would be confirmed with the business in a real project.

## 3. SQL (`Queries.sql`)

1. **Won deals and revenue per source**: count and total revenue of won deals, ordered by count.
2. **Top 10 customers by revenue**: total deals, revenue and average deal amount among won deals.
3. **Repeat buyers**: customers (joined with `customers`) with more than 2 won deals.

## 4. Baseline ML (`Baseline_ML.ipynb`)

**Task:** multiclass classification of `status` (won / lost / in progress).
**Features:** `amount`, `age` (numeric); `source`, `city` (categorical).
**Final dataset:** 3002 rows after removing rows with unknown status/source and missing/suspicious amounts.

### Leakage prevention

- The train/test split (80/20) is **grouped by `customer_id`** using `GroupShuffleSplit`, so every deal of a given customer goes entirely to train or entirely to test. This prevents the model from recognising customer-level features (`age`, `city`) seen during training.
- Imputation (median / most frequent), scaling and one-hot encoding live inside a `ColumnTransformer` + `Pipeline`, so they are fitted on training data only. `deal_id`, `customer_id` and the flag columns are not used as features.
- The test set is used only once, for final evaluation.
- Cross-validation during hyperparameter tuning uses row-level `StratifiedKFold` (a known simplification; the grouped split is applied at the outer level).

### Models and tuning

- `DummyClassifier` (benchmark), `LogisticRegression`, `RandomForestClassifier`.
- Tuned with 5-fold `StratifiedKFold`: `GridSearchCV` for Logistic Regression, `RandomizedSearchCV` (40 iterations) for Random Forest.

### Results (test accuracy)

| Model | Baseline | Tuned |
|-------|----------|-------|
| Dummy (most frequent) | 0.348 | 0.348 |
| Logistic Regression | 0.374 | **0.378** |
| Random Forest | 0.334 | 0.348 |

### Interpretation

All models score close to 33-38%. This is **expected**: the synthetic data is generated with independent uniform random values, so there is no real relationship between the features and `status`. The goal of this task is a correct, leakage-safe pipeline rather than a high score. The model is not production-ready and the numbers should not be read as business insight.

## Reproducibility notes

- The ML split and models use `random_state=42`.
- `data_generation.py` uses `random.seed(42)` for fully reproducible runs.
- The database connection string is read from the `DATABASE_URL` environment variable; credentials are never committed.
